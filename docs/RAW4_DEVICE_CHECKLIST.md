# 当日の12MP診断手順（準備用・実機未実施）

関連: #78（RAW4保存側比較）、#204（編集プレビュー第1段階）、#208（当日のプレビュー確認）。
本書は操作の準備であり、写真利用・APK導入・実機操作を自動実行するものではない。
24MPは今回先行しない。マージ・製品既定変更も別の明示許可まで行わない。

## 事前にそろえるもの

- 同じPixel 9a、本人が診断に使うと決めた12MP DNGを1つ。原本を変更しない。
- 検証したRAW診断APK、source commit、APK SHA-256、ABI、build条件の控え。
- プレビュー確認は#205〜#207がmainへ入った後、それを含む確認用APKがそろってから実施する。
  RAW診断APKは通常の編集画面・保存FGS・撮影復帰の確認を代替しない。
- 元の写真と対応付ける表、数値report、画面録画はローカルだけに置く。素材名/URI/hash値/撮影情報/
  端末識別子/個人用パス/写真ごとの生の数値をIssue・PR・Gitへ載せない。

署名が合わず導入できない場合、アプリ削除やデータ消去で回避せず止める。APKの成功は写真利用の許可ではない。
端末の明るさ・給電状態・設定を固定し、通常アプリの現像/保存や重い背景処理と重ねない。
発熱が落ち着いてから開始する。OS警告、低メモリ、異常な発熱では取消して止める。端末上限を広げない。

## 1. RAW4の速度（計20回、録画・メモリ観測なし）

1. 診断アプリで「RAW4」を選択。MemoryとReverseはoff。
2. 本人が許可したDNGをFilesで選ぶ。warmup AB＋ABBA×2の計10回を待つ。
3. complete=true・status=SUCCESS・JPEG一致・選択原本不変・private入力削除・owner終了を確認する。
   全JPEGは最初の成功JPEGとfingerprint比較され、不一致で停止する。hash値はreportへ出ない。
4. report全文を選択してローカルのforward.jsonへ保存する。画像ファイルは共有しない。
5. 冷却後、同じAPK・原本・設定でReverseだけonにし、warmup BA＋BAAB×2の計10回。
   成功条件を同様に確認しreverse.jsonをローカル保存する。
6. tools/raw-diagnostic/README.mdの集計手順を使う。同じ原本bytes/APK・端末条件の確認が前提。

判定: 対象工程の中央値が両順10%以上短縮なら性能採用候補、両順未満は今回条件で見送り。
順序で10%判定が違う場合だけ追加順序比較。tone/色区間が両順10%以上短縮したらR7単独比較で切り分ける。
見送りは条件と結果を試した案の一覧へ残す。10%は性能上の物差しであり安全・品質合格の代替ではない。
全体時間と未分解残差も記録するが、全体が横ばいという理由で対象工程の短縮を打ち消さない。

## 2. メモリ（別に2回、録画なし）

RAW4のMemoryをon、Reverseをoffへ戻し、同じ12MP DNGでA/B各1回の計2回だけ行う。初回除外の速度測定には使わない。
100ms目標のmanaged/native使用量は「観測最大」であり瞬間peakを保証しない。PSSは前後のみ。
sample数・実間隔・最大gap・観測費用・欠測と終了確認を残す。各最大値を足して同時peakと呼ばない。
失敗・中断・owner未終了なら完了に補完しない。24MPは別途実施を決めるまで選ばない。

## 3. 取消（別に2回）

「Select DNG for 2 cancellation checks」から同じDNGを選ぶ。
RAW4 onのdecode完了後、Foundation完了後に1回ずつ自動取消し、完了結果なし・部分JPEGなし・
owner終了・原本不変を記録する。native処理内部の任意の瞬間の取消を保証する試験ではない。
失敗scratchは既存owner契約どおり私有領域へ残る。owner終了とscratch完全削除を混同しない。
本人が画面を離れる/Cancelを押すとsession自体が停止する。その中断を期待した2回の成功へ数えない。

## 4. #208の操作録画とプレビュー確認（前提APKがそろった後）

保存側の試行と同時に動かさない。同じ機会に実施してよいが、#208は保存速度・24MP・顔保護写真を対象としない。
対象は12MP DNGで、写真を開く、強度、色温度、明るさの4操作。各操作を1回慣らした後3回ずつ記録する。
#205の通常MANUAL_TRIAL内訳は呼び出し側のTRIAL_RENDER統合区間までで、工程内部の細分化を含まない。
保存側とプレビュー側は別測定だが、プレビューのログと録画はこの同じ16操作で取得し、追加16操作は要求しない。
各調整の開始値/終了値・動かす速さをそろえ、指を離すまでと離した後を区別する。発熱/充電状態を残す。

- #205の工程内訳と同じ操作を端末標準の画面録画で確認する。録画ありと明記する。
  録画負荷があるため、保存側の録画なし測定や過去の録画なしの値と同条件の速度として混ぜない。
  録画負荷を切り分ける追加試行を自動で増やさず、必要なら別Issue/実施判断にする。
- 録画はマイク音声off、通知や個人情報が映らない状態を本人が確認してから開始する。
  端末設定/権限をこちらから変更しない。録画ファイルはローカルだけで扱い、Issue/PRへ添付しない。
- コマ送りで、操作開始・指離し・新しい表示が現れた時刻を読む。可変fpsでは単純なコマ数/公称fpsではなく
  各フレームのtimestampを使う。接触点が分からない録画では指離し時刻の不確実さを明記する。
- 「視覚的に安定した表示」と「最新要求の正確な表示」は別。#205の適用世代/完了記録と対応付けられない場合は、
  録画だけで正確な表示の完了を断定しない。対応が不足したら不足を記録し、診断修正は別Issueへ切り出す。
- 操作中の更新間隔、指離しから正確な表示、写真を開いて初表示までを別集計し、各操作の中央値と
  #204の目標を並べる。内部工程時間を操作から表示までの体感時間へ読み替えない。
- 熱などで3回そろわなければ取れた回数と条件を記録する。埋め合わせを続けず、追加計測は新Issueとする。
  目標到達の有無と別に、記録と第2段階の起票/見送り/保留の判断で#208を区切る。

## 所要目安と終了

同じ診断APK/12MP入力の1回の実測時間をTとすると、速度だけで約20T。
これにメモリ2回の観測負荷を含む時間、取消2回の到達/回収時間、入力選択・照合・冷却が加わる。
例としてT=35秒なら速度部分だけ約12分だが、これは計算例であり今回APKの予測/実測ではない。
プレビュー確認は4操作×（慣らし1＋測定3）の計16操作と、コマ解析の時間が必要。
準備・冷却・録画解析を含む終了時刻は約束しない。途中の熱/失敗ではその場で区切り、当日中の完走を強制しない。

終了後、私有report/録画の保管先を本人が確認し、共有するのは操作/工程の集計と採否理由だけに絞る。
実機操作や公開は個別の許可範囲に従う。合成試験の成功をこの当日チェックの完了へ付け替えない。

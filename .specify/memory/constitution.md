# Cinematic Camera Constitution

## Core Principles

### I. 現行仕様と変更記録の分離

ユーザーの合意した製品方針を要件の根拠とし、[Living Spec](../../specs/README.md)で現在の観測可能な振る舞いと不変条件を管理する。
改修ごとに仕様の系列を増やさず、機能単位の既存文書を更新する。変更目的・計画・差分・タスク・進捗・検証証拠・採否は Issue / PR に置く。
長期的な技術設計は docs、再実行する手順は docs の手順書に置く。ツールが生成した作業成果物を自動的に現行仕様の正本にしない。
PRの変更案はマージまでは現行契約ではない。未採用・既定オフ・検証限定を製品機能と混同しない。
旧番号付き資料は重要契約と参照を移すまで保持し、集約済み範囲では Living Spec を優先する。未集約の詳細は参照先に残ると明示する。
仕様・実装・実測の不一致を隠さず、未確認を合格としない。

### II. Android標準APIを出発点にする

Android標準API、Jetpack、一般的なlifecycleと権限の扱いを優先する。標準から外れる必要が
実測された場合だけ、代案・理由・対象範囲を対応する技術設計へ記録する。CameraX管理の
CameraDevice / sessionを直接操作せず、独自回避やCamera2全面移行は合意なく進めない。

### III. 実装・受付・実測・合格を分ける

設定要求が受理されたこととセンサーへの反映、ファイルが保存されたこととDNGの有効性を
分けて記録する。ビルド、静的レビュー、エミュレーターの結果をPixel 9a実機の合格にしない。
未検証は未検証のままとし、端末非対応は実測した能力・エラー・再現条件で裏付ける。
実機確認待ちだけで、合意した範囲の次の限定作業を一律停止しない。ビルド・自動テスト・独立レビューで
確認可能な範囲を進め、残る実機確認を明示する。重大な欠陥・テスト失敗・権限判断・大幅な範囲拡大は停止して報告する。

### IV. ローカル保存と公開情報の境界

撮影物は合意した保存先で扱い、ログはアプリ専用領域に保持する。RAW撮影ではDNG原本を非破壊で維持し、
撮影時の仮JPEGはアプリ内部だけに保存する。DNG原本と現像成功後のJPEGを標準MediaStoreの
`Pictures/Cinematic Camera/`へ保存する。通常のJPEG単独撮影は現行の共有保存を維持する。
共有DNGの1つを永続原本として編集・現像から読み取り参照し、恒久的なDNG二重保存を避ける。
撮影/共有失敗時の一時DNGは保全し、共有先の完全性と台帳への引渡しを確認した後だけ解放する。
失敗・中断時も受領済みDNG/仮JPEGを保全し、既存写真を移動・削除しない。バックエンドを導入しない。
詳細は[原本・編集情報・保存の現行仕様](../../specs/storage/spec.md)に従う。自動現像の将来計画と現在の手動保存経路を区別する。
秘密、認証情報、署名秘密、個人情報、個人用絶対パス、撮影物、会話ログ、端末固有識別子を
リポジトリや配布ZIPへ入れない。要求されるカメラ能力やAndroidビルドの記録と、公開可能な
検証要約を区別する。サンプルに実ユーザー名や実端末の固有識別子を使わない。

### V. 限定した範囲と適切な検証

依頼された範囲を明確にし、依存や検証基盤を必要以上に増やさない。合意した CameraX 1.6.2 の固定を無断で変更しない。現在の対応条件は Living Spec、依存の実値はビルド設定を確認する。
P0 はプレビュー・RAW・マニュアル露出の成立性を調べた段階として扱い、当時の対象外を現在の製品全体へ適用しない。
機械的な検証と実機の受入条件を分け、GMD等の利用は現行の共有手順に従う。

### VI. ライブ品質・原本保持・少数の完成したルック

最優先用途はライブパフォーマンスの静止画/動画撮影とする。P0を維持し、P0.5で暗所・動体・照明・音声・
応答/熱の制約を先に検証する。Stage Clearを最優先とし、Stage Dramatic / Cinema T&Oが続く。
ライブは元画角・解像度・RAW原本を可能な限り保持し、編集定義と分離する。撮影時横長固定を必須にしない。
写真/動画でルックの意図を共通にするが、入力形式・色空間の違いを無視しない。
UI/アイコンは無機質・メカ感を軸とする複数案を比較し、ユーザーが最終選択する。

## 技術・公開上の制約

- Kotlin / Jetpack Composeを基盤とし、現在の構成と採用範囲は実装・Living Specで確認する。P0当時のRAW現像、NDK、GPU/LUT、動画、
  21:9保存、SNS、ギャラリー、クラウドの別フェーズという記録は歴史的境界であり、現在の実装状況を示すものではない。
- P0の完了判定と停止条件は機能specと`docs/P0_REPORT.md`で追跡する。実機AC3/4が
  不成立なら根拠付きBLOCKEDとして記録し、採否判断を勝手に補正しない。
- 後続方針は`specs/002-live-capture`で扱う。優先順はP0.5ライブ技術検証、P1 Stage Clear、
  P2写真/動画の画作り統合、P3非破壊編集/出力/共有/製品UI、後続custom/LUT編集とする。
  安定SDRを先行し、HDRは実能力照会と標準APIで成立する対応modeへ限定する。高度なHDR処理や
  先行モジュール追加へ広げず、実装は依頼された範囲だけ進める。
- 署名秘密の新規生成・継続利用設定、Secrets登録、他projectの鍵の流用を無断で行わない。
  P0用の一時debug署名と、継続更新用の固定署名を混同しない。
- 公開範囲を変える前に、全Git履歴・branch・文書・workflow・配布物・公開されるログを検査する。
  問題が過去の履歴に残る場合、最新削除で解決扱いにせず、破壊的な履歴変更は相談する。

## 開発とレビュー

基本の流れは Issue で範囲を定義し、現行仕様と実装を確認して必要な仕様更新・設計・実装・検証を行う。
Spec Kit の必要な手順を利用するが、改修ごとの全生成物をリポジトリへ恒久保存することは要求しない。
作業の完了状態と実機の合格状態は Issue / PR で区別し、標準 skills を直接書き換えない。

初回main初期化後は作業branchとDraft PRを使い、現在のheadのCI・レビュー・未解決会話を確認する。
利用者のmerge許可がなければmerge前に停止し、APPROVE代行、admin merge、チェック免除、
保護回避をしない。機械的検証は実際のAndroid workflowに合わせる。文書は原則日本語とする。

## Governance

本Constitutionは本リポジトリのspec、plan、実装、レビューへ適用する。ユーザーの明示指示と
作業範囲を優先し、衝突や未決事項を隠さない。改訂時は理由・影響・必要な移行をPRに記録する。
原則を壊す変更はMAJOR、新原則追加はMINOR、意味を変えない明確化はPATCHとする。
1.0.0はP0と公開・レビュー上の合意を初めて明文化した版。1.1.0はユーザーの追加要件に従い、
新撮影の共有画像保存を原則IVへ明記した。既存写真の移行・一括削除や新しい広範囲ストレージ権限は導入しない。
1.2.0はライブ品質・原本保持・Stage Clear優先と新しい段階構成を追加したMINOR改訂。
既存P0のAC・コード・依存の変更や、P0.5以降の実装済み宣言を伴わない。

1.3.0は合意済みのRAW撮影後保存方針を原則IVへ追加したMINOR改訂。DNGの共有保存先と既存写真は維持し、
仮JPEGを内部へ、現像成功JPEGを共有へ分け、共有DNGを唯一の永続原本とする。一時DNGは検証済み引渡し後に解放する。
段階的な実装・移行境界はspec016で扱い、
この文書の変更だけでアプリの保存コードを切り替えない。merge前はDraftの改訂案として扱う。

1.4.0 は Living Spec と変更記録の責務を分離した MINOR 改訂。アプリの挙動・保存出力・権限・CI・マージ条件は変更しない。旧資料は移行確認まで保持する。改訂理由と移行範囲は Issue #231 と対応 PR を参照する。

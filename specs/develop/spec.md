# 編集とプレビューの現行仕様

## 通常の編集経路

- 通常のカメラロールは手動試験現像（MANUAL_TRIAL）へ接続する。最大1024pxの表示と、対応DNGの原寸試験JPEG保存を提供する。完成品質の自動FULL現像とは別で、顔保護なし・診断露出・暫定色の制約を明示する。
- 強さは0～100の整数入力（内部0～1）、相対色温度は−100～100、明るさは−2～2EV。既定値は強さ50・色温度0・明るさ0。相対色温度をKの絶対値と表示しない。
- 撮影と同じ中央選択の目盛りと近傍値を使う。左ドラッグで増加、右で減少。1段24dp、左右タップは1段で、絶対位置へジャンプしない。
- 基準値（50/0/0）では一旦止まり、追加8dp相当の移動で離れる。到達時にクリック触覚を1回要求し、離脱後の再到達は再度要求する。OS・Viewの触覚設定を尊重する。
- 編集対象キーを背景・上辺線・読み上げの選択状態で示す。画像領域→キー→保存操作の配置と、状態帯両端の戻る・情報の固定を維持する。編集目盛りは画像領域の下部へ重ねる。
- モードは「試験 1024px」のみアンバー、手動試験とStage Clearは白枠。「顔保護なし」はモードとは別の注意で、手動/縮小試験ではアンバー、Stage Clearでは非表示。チップ非表示だけで顔保護が実装済みとは判断しない。
- 比較キーと下段切替は両方残す。比較元は撮影時WBのRAW基準表示（R7・ルック・手動調整なし、暫定色）で、強さ0の結果とは別。

## 再開時の撮影・資源状態

- Androidが編集画面だけを復元し、撮影Activityがまだ存在しない場合も、原本と編集値を再検証して現像を再開できる。撮影画面を一度開くことを復元の前提にしない。
- process内の撮影作業はmain threadで中央登録先から観測する。正常に読めた登録0件は「このprocessの撮影作業なし」であり、観測失敗とは区別する。撮影開始前にownerを登録し、撮影callback・writer・録画の終了処理が完了するまでは保持する。
- 未確認のowner、読取失敗、main threadの観測timeoutは引き続き停止条件とする。登録0件だけでOS側カメラの解放を推測せず、CameraManagerの利用可能通知、foreground、温度、メモリ、作業容量の確認を別途必要とする。
- 停止通知は実際に確認できない/許可されない項目を示す。高温やメモリ不足を一律に「撮影を終了」と案内せず、観測不能と確認済みの不足を区別する。

旧[025の計画](../025-private-trial-ui/plan.md)にある「ownerなしは不明」は、本節の正常な空集合と観測失敗を区別する契約で置き換える。

## 画像領域と一時表示

- 画像は縦横比を保つ全体Fitとする。画像領域の下辺は編集目盛りを閉じた状態のキー列直前へ固定し、目盛りを開閉しても画像の位置・サイズを変えない。開いた目盛りは画像下部を覆い、閉じれば下端まで見える。
- 同じ写真の再計算中は直前の表示を残し、更新中であることを読み上げを含めて示す。別写真・背景化・当該要求の原本検証失敗では表示を破棄する。古い要求の失敗や完了で最新表示を消したり上書きしない。
- 進捗・一時通知・進行中の保存通知は画像領域へ重ね、領域寸法を変えない。編集目盛りを開いた場合の進捗・通知はその上に配置して隠さない。詳細情報は標準ダイアログで開く。
- 保持するのは最大1024pxのUI所有の表示/比較Bitmapで、原寸やRAW配列を追加保持しない。新結果への置換後は既存の所有権に従って旧Bitmapを解放する。
- 保持した表示画像を保存済み・最新計算済みとは扱わない。更新開始時に旧保存handleを外し、保存可否は既存の確定・照合条件で決める。
- 小画面・大きい文字では既存の全体スクロール条件を保つ。通知と目盛りの高さが画像領域を超える場合は、その重ね表示部分だけを縦スクロールし、画像領域の寸法・親内位置を変えず再試行と目盛りの両方へアクセスできるようにする。明示的なスクロール操作では、既存の全体スクロールや標準のスクロール連携によって画面上の位置が移動し得る。

## ドラッグ中と確定後

- 手動試験のドラッグ中は最大256pxで同じ処理を回し、指を離すと最新確定値で最大1024pxを再計算する。
- 同じ写真の直前の正確な処理で得た自動判定・測光値を粗表示で再利用する。色温度/明るさの操作中に少し古い値を使うのは表示限定の近似。判定値がなければ既存表示を保つ。
- 粗表示は実行1件・待機最新1件とし、入力のたびに実行中の処理を中断する方式にはしない。同じ画面の粗表示と正確表示は排他し、確定・取消・写真切替・背景化で古い結果を失効させる。
- 粗表示には保存handleを渡さない。確定結果が表示されるまでは「閉じる」で編集値を確定保持したり、JPEG保存へ昇格させたりしない。
- 取消・RESET・キーボード・支援技術・写真/項目/セッション切替の入力境界を守り、遅い応答で別写真や最新値を上書きしない。
- 原本と編集情報は分離する。編集値の復元・JPEG保存条件は [保存の現行仕様](../storage/spec.md) に従う。

## プレビューでの原本確認

- 写真を選び直す・再開する時は原本全体の SHA-256 を確認する。展開時も検証済みの一時 snapshot を使い、展開後の原本全体照合を残す。以後の表示計算は保持した縮小入力だけを使い、DNG を書き換えない。
- 同じ手動試験セッションの確定表示・1024px比較画像・確定表示の採用前は、標準プロバイダのサイズと更新日時、公開/所有状態、読取権限を確認する。変化・削除・アクセス失効では表示と一時入力を失効させる。別写真・背景化・画面終了ではこの確認状態を再利用しない。
- ドラッグ中の256px粗表示と比較画像は、検証済みの保持入力だけを使い、プロバイダ確認やSHA-256照合を行わない。取消・写真/世代・ライフサイクル・メモリの条件は維持する。ドラッグ中の原本変化は次の確定時に確認し、粗表示を保存や完成結果へ昇格させない。
- 診断では照合経路（粗表示での省略、metadata、更新日時不明/観測なしのSHA、session直接SHA）と所要時間・成否を匿名で記録する。省略は0nsと明示し、従来のVERIFY区間と同じ仕事を測った値として比較しない。
- この軽い確認は内容一致の保証ではない。同一サイズ・同一更新日時の差し替え、MediaStore の時刻情報への未反映は見逃し得る。保存に使う URI・bytes・SHA-256・grant は最初の強い確認値から更新せず、保存前後の全体照合を維持する。
- 更新日時が不明/欠落/0以下のプロバイダでは互換性のため従来の全体照合へ戻す。軽い確認の成功を保存可否や現在のファイル内容の証明へ昇格しない。

## 写真表示のメモリ条件

- 通常CPU経路では、写真表示の受付と原寸保存の受付は同じqueue/ownerの中で区別する。手動試験プレビューはOSが低メモリと判断した時、観測不能時、空きメモリ値が不正な時に停止する。撮影優先・foreground・温度・作業容量・取消・所有資源の解放確認は従来どおり必要とする。
- 初回の原寸native decode直前と原寸保存には従来の768MiB空き条件を残す。これは測定済みの必要最小量ではなく、保守的な既存条件である。展開後の縮小、保持した1024px/256px入力の再編集、比較Bitmapには原寸用768MiBや保存受付の512MiBを再要求しない。
- OSの `MemoryInfo.lowMemory` を現在値として確認し、既存の500ms観測と処理境界の確認を併用する。`onLowMemory` や実行中の `onTrimMemory` 通知だけには依存しない。これらの低メモリ通知はAPI 34以降配信されない。
- 表示の割当失敗は結果を採用せず、失敗したsessionの縮小入力・一時ファイル・descriptorを解放する。解放失敗時はownerを保持する。原本と編集値を保ち、利用者の明示再試行で新しいsessionを作る。通知による停止や失敗したsessionを自動復活させない。
- 比較Bitmapの割当失敗だけは従来どおり任意のBefore欠落として扱う。原本変化、取消、IO/close失敗、OS低メモリの確認は無視しない。保存の原寸条件と公開境界は弱めない。
- 受付成功やOOM処理は、確保成功やOSによるprocess終了の回避を保証しない。合成観測と注入試験を実機の低メモリ耐性・必要RAMの合格に読み替えない。

公式根拠: [MemoryInfo](https://developer.android.com/reference/android/app/ActivityManager.MemoryInfo)、
[ComponentCallbacks2](https://developer.android.com/reference/android/content/ComponentCallbacks2)、
[ComponentCallbacks](https://developer.android.com/reference/android/content/ComponentCallbacks)。

## 診断版だけの GPU 編集経路（#287）

- 通常 debug / release は GPU を既定とし、保存済みの診断用選択を読み込まない。専用 gpuDiagnostic の診断 Hub では CPU/GPU を明示選択でき、その他の診断 variant は従来の CPU 既定を維持する。通常の設定画面へエンジン切替は置かない。GPU 失敗時も CPU へ自動回避せず、既存の GPU retry / HOLD 契約を使う。
- GPU 選択時は同じ現像画面・画像領域・固定比較キャプション・Fit 配置を使う。撮影時 WB の線形入力を既存 snapshot → RGB16 → BOX 経路で一度準備し、物理的な向きを直した入力を GPU 表示へ渡す。入力上限は長辺1024pxかつ786,432画素で、通常 CPU の寸法条件を変えない。
- 強さ・色温度・明るさは GL の最新値へ送る。256px粗表示・CPU描画・フレームごとの原本照合・フレームごとの保存世代作成は行わない。実際に表示した値が確定値と一致するまで閉じる・保存へ昇格しない。比較操作は既存の長押し・比較ボタン・下段切替・読み上げ操作を維持する。
- Files選択後は前面復帰だけで読み始めず、既存観測のカメラ利用状態と受付条件、表示面を待つ。通知を使う最大10秒の受付待機で、GPU専用のpollingや固定sleepを加えない。待機の取消・別写真・背景化では旧要求を開始しない。受付成功後のnative展開時間を待機上限に含めない。
- 選択後の失敗は選択した写真の画像領域に表示する。GPU能力不足・context喪失・メモリ予算・表示面解放未確認は「GPU を使えません」と再試行を示し、CPUへ自動で切り替えない。
- Surface破棄は最大2秒で区切り、時間超過をアプリの未処理例外にしない。未完了の破棄ownerを保持し、旧Surfaceへの表示を止める。再試行/写真切替は旧ownerの終了確認後だけ新しく開く。
- 写真切替・画面終了・背景化ではGL写真/表示面/入力/コールバックを閉じる。UI_HIDDEN（20）以上のtrimも同じプレビューownerだけを終了し、10ではこのtrim契約による解放を行わない。foreground exportの所有資源を解放しない。
- GPUプレビューと原寸保存は同じ DevelopEngine 設定を参照する。診断用ビルド限定のプレビュー接続は #339 で先行統合し、#286 の保存接続は別途検証する。通常版のGPU有効化や既定変更は含まない。GPU経路の実機品質・速度・Gate 2合格はこの仕様で主張しない。

### Draft: GPU入力準備と保存の並行動作（#350）

GPU経路では、別写真の原本確認・preflight・入力生成を専用の単一ownerで行い、foreground exportと並行できる。保存用の世代・journal・publicationは従来のqueueで直列に扱い、GPU入力が確認した原本とgeometryを保存準備へ渡す。通常CPUの受付・入力準備は変えない。写真を開く際の768MiB条件や撮影優先・温度・取消・確実な資源解放は維持する。同じ保存中写真の再選択は暗黙のプレビュー再開にせず、未確定保存の確認とREADY/PUBLISHED後の明示再開を必要とする。詳細と検証待ちの条件は[保存仕様](../storage/spec.md)と[GPU保存統合](../../docs/GPU_EXPORT_SAVE_INTEGRATION.md)を参照する。この既定化変更は PR のマージまで提案であり、実機合格を意味しない。

## 製品に採用していないもの

- process共通の直列受付（PreviewSerial）は診断の明示指定だけで通常オフ。同一画面内の粗/正確処理の排他とは別。
- PreviewPixelExecution の1/2並列候補は通常のプレビューには接続しない。統合診断版だけは実編集画面から明示的にオン・オフでき、既定オフとする。保存で採用した並列化が自動的にプレビューへ適用されるわけではない。
- GPU検証基盤・表引きなどの候補が main に存在しても製品採用とはしない。既存CPU golden、原本、保存出力を無断で置き換えない。
- 256px・1024pxというサイズは操作から表示までの所要時間を保証しない。計算ログ・画面反映・利用者の操作感は区別する。

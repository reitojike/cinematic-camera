# 現行仕様（Living Spec）

リポジトリに残す仕様は、機能ごとの**現在の振る舞いと不変条件**です。変更のたびに同じ文書を更新します。
改修目的・変更案・差分・実装タスク・進捗・計測値・レビュー結果は Issue / PR に置きます。

## 現行仕様の入口

- [撮影と制御](capture/spec.md)
- [カメラロール](library/spec.md)
- [編集とプレビュー](develop/spec.md)
- [原本・編集情報・保存](storage/spec.md)
- [設定・診断・対応範囲](diagnostics/spec.md)
- [アプリ共通メッセージ](ui-messages/spec.md)（部品基盤。既存画面への適用は別PR）

この一覧の文書はマージ済みの製品契約を扱います。検証用コードが main に存在することと、製品に採用済みであることは別です。
実機の成功・速度・画質は、対象と条件を特定した Issue / PR の証拠で確認します。仕様が存在するだけで合格とは扱いません。

## 番号付き資料の移行境界

既存の番号付きディレクトリは、設計・契約の取りこぼしを防ぐため移行中の参照資料として保持しています。
現行仕様の各文書に集約した範囲では、その文書を正とします。まだ集約していない詳細契約はリンク先の旧資料を参照し、
後続のマージ済み変更・実装と照合します。旧資料の `Draft`、承認待ち、当時の対象外、完了チェックは現在の進捗の正本ではありません。
矛盾や未実装の計画は勝手に現行仕様へ昇格させず、Issue で確認します。

番号付き資料をこの一覧と同時に全面削除しません。重要な契約は Living Spec、長期的な技術設計は docs、
試験・運用の再実行手順は docs の手順書へ移してから、参照と Git 履歴からの復元可能性を確認して整理します。
移行対応表・残件・完了証拠は [Issue #231](https://github.com/reitojike/cinematic-camera/issues/231) で管理します。

## 更新の原則

1. Issue で目的・範囲・対象外・完了条件・停止条件を定義する。
2. 既存の現行仕様を確認する。振る舞いが変わる場合は同じ PR で該当する機能仕様を更新する。
3. 振る舞いが不変の最適化・内部整理では、不要な新規 spec を作らず、必要な設計・検証証拠を Issue / PR に残す。
4. PR 内の仕様変更は提案であり、マージまでは現行仕様を置き換えない。未採用・既定オフ・実機未確認を明記する。
5. Spec Kit の手順を使う場合も、その生成物を自動的に正本としない。ツール利用方法は [SPEC_KIT](../docs/SPEC_KIT.md) を参照する。
